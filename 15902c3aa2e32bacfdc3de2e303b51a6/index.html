Core4 Platform: Scope

Scope. Quality. Cost. Time. Working scope for the Core4 delivery platform, built to the Dutch practical guideline NEN NPR 5333, with functional sizing per NESMA (ISO/IEC 24570) and quality expressed in the ISO/IEC 25010 model, measured per ISO/IEC 25023 and ISO 5055.

1. Why Core4

Managers cannot make firm commitments on scope, quality, time and cost when the only thing they get back from their teams is best effort. The board asks for clear commitments for the year; the teams plan a sprint or a PI ahead and will not promise more. The manager in the middle has no objective read on what is actually being delivered, no fair way to compare one application against another, and no way to tell whether a supplier price is reasonable.

Core4 closes that gap. It pulls together data that today sits in separate systems (source code analysis, Jira, Oracle hour registration, the certified function point count, the contract) and turns it into one comparable picture per application. From there the four sides of software delivery can be steered together:

DirectionDimensionThe question it answers
FasterTimeAre we delivering predictably and on time?
BetterQualityIs the software secure, reliable and maintainable?
HappierSatisfactionDo the teams, the business and the users value the result?
CheaperCostAre we getting fair value for the money spent?

2. What the platform is

Core4 is a steering and reporting layer. It reads from the source systems and never writes back to them; it is not a system of record. Data is refreshed on a periodic batch, aligned to the cadence of the certified function point count rather than in real time, which keeps it cheap to run and matches how the underlying numbers are actually produced.

The platform is delivered in three levels. Each level stands on its own and adds steering ability:

LevelNameWhat it makes steerable
Level 1Basic predictabilityVelocity, load and flow predictability: can we forecast at all
Level 2Quality and satisfactionISO 5055 quality, MTBF and MTTR, team, collaboration and usage happiness
Level 3Productivity and outputProductivity in hours per FP, delivery speed in FP per iteration, output tariff

The first release covers Levels 1 and 2 together with the Level 3 output metrics (productivity, delivery speed and the output tariff), because those make the cost and time picture readable in function points. The remaining Level 3 contracting mechanics, and automated function point sizing, come later.

In the first release

  • The dashboard: applications as columns, the metric groups as rows, colour coded, with the source behind every value one click away.
  • Steering controls: organisational level, reporting period, and an org roll-up.
  • The Level 1 and 2 metric set, plus the Level 3 output metrics.
  • The function point driven cost, throughput and forecast views.
  • The FPA management screen, where the certified count is viewed and maintained.
  • Forecast and variance views (Actuals, Estimate to Complete, forecast at completion, variance against the baseline) for cost, time and scope.
  • Side by side comparison of similar applications.

Not in the first release

  • Automated function point sizing from the source code.
  • Write back to Jira, Oracle or any other source system.

Story points run the agile teams; function points carry the business value. Story points are team specific and subjective, so everything that gets compared across applications or used in a contract (cost per FP, throughput, remaining scope) is expressed in function points.

4. Function points and sizing

Function points are the backbone of the cost and time views, so where they come from matters. They come from an Excel workbook maintained by a certified function point counter, which Core4 imports. The platform does not run automated source code sizing in the pipeline for the first release. A certified count is auditable, supplier neutral and holds up in a contract, which is exactly what is needed to make cost per FP and productivity defensible. Automated sizing tooling (CAST, BonCode, ScopeMaster) is faster but measures the code that exists rather than the functionality that was asked for; it has a place later, as a cross check, never as the contractual number.

The counting method is set per application, following the recognised functional size measurement standards: NESMA (ISO/IEC 24570), of which NEN NPR 5333 is the Dutch practical guideline, and IFPUG (ISO/IEC 20926). The standard IFPUG set is used here:

MethodFunction types
IFPUG (used here)EI external input, EO external output, EQ external query, ILF internal logical file, EIF external interface file

COSMICData movements (entry, exit, read, write)
EFSA simplified set

The number of function points is not typed in by hand; it follows from the type and the complexity using the standard IFPUG weights. A real sheet runs to several hundred functions, so this rule keeps the count consistent and auditable across all of them:

TypeLowMediumHigh
EI external input346
EO external output457
EQ external query346
ILF internal logical file71015
EIF external interface file5710

Complexity therefore does two jobs: with the type it fixes the function point count through the table above, and it also sets the price on output based work and the effort estimate on hour based work (see section 5).

From this one sheet the platform derives delivered FP (everything deployed), remaining scope, throughput, the lead times between stages, and cost per FP. The certified counter works in the FPA management screen, where the sheet can be uploaded and the functions, their complexity, status, dates and cost maintained in the browser. Every change is recorded in an audit trail.

5. Cost models

Every application is either hour based (time and materials) or FP based (output). A single toggle per application sets which model runs, how the estimate to complete behaves, and whether the output tariff applies. Both models feed the same cost per FP figure so applications stay comparable however they are priced.

ModelHow cost is builtInputs
Hour basedHours times the rate cardOracle hours, rate card
FP basedThe price of each delivered functionFPA cost, set from the function price book by complexity band

On output based work, each function carries a price set by its complexity band together with its function point count; that price comes from the function price book and lands in the cost column of the FPA sheet. This is the basis of the Level 3 output tariff, and it is already usable now to express cost as delivered functionality rather than hours burned.

The estimate to complete behaves differently in each model. On hour based work it is genuinely an estimate: the remaining functions are translated into expected hours, weighted by their complexity, and priced at the rate card. On FP based work it is accurate, because the price of each remaining function is already agreed. Complexity is what makes both possible, which is why it sits in the FPA sheet alongside the count.

Rates are held per role and per vendor. The output tariff and the rate card both come from the contract.

6. Forecasting and variance

For every application Core4 tracks where it will land against what was agreed. The forecast completion date is calculated from historical throughput (the FP actually deployed per week) blended with the expected throughput, applied to the remaining scope.

Cost, time and scope each carry the same set of figures against a baseline:

DimensionBaselineActualsEstimate to completeForecast at completionVariance
CostAgreed budgetSpend to dateRemaining, estimated or agreedActuals plus estimateBudget minus forecast
TimeTarget deadlineElapsed to todayRemaining duration from throughputForecast completion dateDays early or late
ScopeScope target in FPDelivered FPRemaining planned FPTotal FP at completionTarget minus total

Scope is the interesting one. Set a scope target in function points; every new feature is a new row in the FPA sheet, so the total scope climbs above the target and the variance shows scope growth in function points. Building less than the target is not a problem and is not flagged; growth beyond it is.

Quality is steered differently. A forecast at completion of a quality score has no clean meaning, so quality is held to a target threshold and shown red, amber or green against it rather than forecast.

The baselines (budget, deadline and scope target) are set by the project owner per application.

7. Organisation and roll-up

Applications roll up through the the Customer hierarchy, from LSTO down to BPSO down to Airside. Choosing a level rolls the metrics up to it; money and function points are summed, percentages and scores are averaged. The pilot applications are AODB (Airport Operational Database), CiSS (Central Information System), IP&F (Integrated Planning and Forecasting) and ACRO.

8. Thresholds, ownership and roles

Red, amber and green are set against bands configured per category (Better, Happier, Cheaper, Faster) rather than per individual metric. The project owner owns the bands for their application; for example only the application owner can change the thresholds on his applications. Sensible defaults ship with the platform and the owner tunes them.

Hours, and therefore spend, come from Oracle, which is the financial system of record. Jira is used for the story point flow metrics and for incidents, not for cost, so time is never counted twice. An incident is a dedicated issue type in Jira; the ticket opening counts as the failure and its resolution as the restore, which is what MTBF and MTTR are calculated from. Azure DevOps stands in for Jira on the flow metrics for any team that runs on it.
